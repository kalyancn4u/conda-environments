# How Lockfile Generation Works — From Zero to Mastery

> A teaching companion to [`README.md`](README.md) (which lists the *commands*). This
> document builds the **mental model**: what a lockfile really is, why it exists, what
> happens at each step of generating one, and how to reason about it with confidence.
> No prior conda knowledge assumed — read it once, top to bottom.

---

## 1. The problem lockfiles solve: "but it works on my machine"

You install some packages, your notebook runs, you share the project. A month later a
colleague (or *future you*, on a new laptop) installs "the same" packages — and it
breaks. Why? Because between then and now, some library released a new version, and the
loose recipe you shared said "give me pandas" without saying *which* pandas.

There are **two different jobs** here, and confusing them causes most of the pain:

| Job | Question it answers | The right tool |
|-----|---------------------|----------------|
| **Intent** | "What do I *want* in this environment?" | a human-written `environments/*.yml` |
| **Reproduction** | "What *exact* bytes were installed, so I can recreate them?" | a machine-generated **lockfile** |

This repo keeps them as **two layers on purpose**:

```
environments/01-core.yml          lockfiles/linux-64/01-core.conda.lock
─────────────────────────         ────────────────────────────────────
loosely pinned INTENT             exact, frozen STATE (URLs + hashes)
"python=3.12.*, numpy, pandas"    "numpy-2.1.3-py312h...conda  #sha256:ab34…"
edited by humans                  generated by a machine; never hand-edited
lets the solver pick fresh        rebuilds byte-for-byte identically
```

**Analogy.** The `.yml` is a *recipe* ("flour, eggs, sugar"). The lockfile is the
*itemized receipt* from one specific shopping trip: exact brand, size, and barcode of
every item, so anyone can buy the identical basket again.

---

## 2. What conda actually does when you "install" (the solve)

When you ask conda for `numpy` + `pandas`, it doesn't just download two files. Each
package declares its *own* dependencies, with version constraints, and those have
dependencies, and so on. Conda must find **one** set of versions where **every**
constraint is satisfied simultaneously — a mini logic puzzle (a SAT/optimization
problem) called **the solve**.

The solve is the slow, clever part. Its output is a concrete list: "to satisfy what you
asked for on *this* operating system, install exactly these 180 packages at these
versions."

> `mamba` is a fast re-implementation of this solver. `conda-lock` uses it under the hood.

---

## 3. What `conda-lock` adds: solve once, freeze the answer

`conda-lock` runs the solve **for you, ahead of time**, and writes the concrete answer to
a file so nobody has to solve again. That file is the **lockfile**. Two consequences:

1. **Reproducibility** — everyone installs the *same* frozen list, not a fresh (possibly
   different) solve.
2. **Speed & safety** — installing from a lock skips solving and verifies each download
   against a checksum.

We generate **explicit** locks (`--kind explicit`): the simplest, most portable form — a
flat list of exact package URLs with hashes, directly consumable by `conda create`.

---

## 4. Anatomy of a lockfile (read one and it stops being magic)

An explicit `linux-64` lock looks like this (abridged):

```text
# This file may be used to create an environment using:
# $ conda create --name <env> --file <this file>
# platform: linux-64
@EXPLICIT
https://conda.anaconda.org/conda-forge/linux-64/python-3.12.9-hab00c5b_1.conda#7c1a...e9
https://conda.anaconda.org/conda-forge/linux-64/numpy-2.1.3-py312h58c1407_0.conda#4d2b...af
https://conda.anaconda.org/conda-forge/noarch/pytz-2024.2-pyhd8ed1ab_0.conda#3e2f...11
...
```

Decoding one line:

```
https://conda.anaconda.org/conda-forge/linux-64/numpy-2.1.3-py312h58c1407_0.conda # 4d2b...af
└───────────── where to download ──────────────┘ └ name ┘└ver┘└ build string ┘      └ sha256 ┘
```

- **`@EXPLICIT`** — tells conda "no solving needed; install these in order."
- **channel + platform** (`conda-forge/linux-64`) — the exact source and OS.
- **build string** (`py312h58c1407_0`) — pins the *compiled variant* (Python 3.12 ABI,
  specific dependencies), not just the version.
- **`#sha256`** — a fingerprint. On install, conda re-hashes the download and refuses it
  if a single byte differs. This is your integrity guarantee.

Because every field is exact, installing this file tomorrow or on a CI server yields an
*identical* environment.

## 5. The end-to-end procedure (the whole pipeline)

```
   environments/01-core.yml
   (intent: python=3.12.*, numpy, pandas, …)
              │
              │  1. conda-lock reads the intent
              ▼
      ┌─────────────────┐   2. mamba SOLVES for a target platform
      │   the solver     │      (linux-64 / win-64 / osx-arm64)
      └─────────────────┘
              │  3. exact version+build chosen for every package
              ▼
   lockfiles/linux-64/01-core.conda.lock
   (state: 180 exact URLs + sha256 hashes)
              │
              │  4. anyone runs:
              │     conda create --name py312-core --file <lock>
              ▼
     an identical, reproducible environment
```

**Step by step, in words:**

1. **Point at intent.** You give `conda-lock` one `environments/*.yml`.
2. **Solve per platform.** For each OS you name (`--platform linux-64`), mamba computes a
   valid, complete package set. *A solve is per-OS* — the low-level binaries differ — which
   is why there is one lockfile **per platform** (§7).
3. **Freeze.** `conda-lock` writes the resolved set as an explicit lockfile.
4. **Rebuild anywhere.** `conda create --file <lock>` downloads exactly those pinned,
   hash-checked packages — no solving, no drift.

The commands that perform steps 1–3 live in [`README.md`](README.md) (GitHub Actions,
Docker, or WSL). This document is about understanding *what each command is doing*.

---

## 6. Why we generate on Linux even from a Windows PC

A `linux-64` lockfile must be **solved against Linux packages**. You don't need a Linux
computer to *use* one, but generating it correctly means solving in a Linux context.
That's exactly why the recommended path is **GitHub Actions** (a Linux runner) or a Linux
container/WSL — the solver sees the real `linux-64` package index and picks the right
builds. Solving `linux-64` on raw Windows tooling would be wrong or impossible.

---

## 7. One lock per platform — and why

The same environment resolves to **different** low-level packages on different operating
systems (compilers, C libraries, and OS-specific builds differ). So each OS gets its own
lockfile:

```
lockfiles/
├── linux-64/   01-core.conda.lock   (solved against Linux)
├── win-64/     01-core.conda.lock   (solved against Windows)
└── osx-arm64/  01-core.conda.lock   (solved against Apple Silicon)
```

A `linux-64` lock is meaningless on Windows and vice-versa — always use the one that
matches the machine you're installing on.

---

## 8. Using a lockfile (the payoff)

```bash
# Recreate the core environment EXACTLY, on a Linux machine:
conda create --name py312-core --file python/3.12/lockfiles/linux-64/01-core.conda.lock
```

No `channels`, no solving, no surprises — conda just downloads the listed, hash-verified
files. This is what makes a result from six months ago rebuildable today.

---

## 9. The lifecycle: when and how locks change

Locks are **snapshots**, so they intentionally go stale as conda-forge moves forward:

1. You edit intent (`environments/*.yml`) — add/remove a package.
2. You **regenerate** the lock (re-run the workflow / command).
3. The new lock captures the new solved state; you commit it (via the PR the workflow
   opens).

The weekly `update-lockfiles` schedule refreshes them even when intent hasn't changed, so
you periodically pick up security and bugfix updates — reviewed through a normal PR.

## 10. Common pitfalls (and the fix)

| Symptom | Cause | Fix |
|---------|-------|-----|
| Lock "doesn't work" on my OS | Using another platform's lock | Use the lock under your platform's folder |
| Regeneration changed hundreds of lines | conda-forge moved on; that's normal | Review the PR diff; it's expected drift, not a bug |
| Solve fails for one env on one platform | No build of some package for that OS (e.g. TensorFlow on win-64) | Expected & documented; that platform is skipped |
| Want to hand-edit a lock | Never do this — it breaks integrity | Change the `.yml` and regenerate |
| Install rejects a package | sha256 mismatch (corrupted/tampered download) | Re-download / clear cache; the hash guard is working |

## Glossary

- **Solve** — computing a complete, mutually-compatible set of packages from constraints.
- **Explicit lockfile** — a flat list of exact package URLs + hashes; needs no solving.
- **Build string** — code identifying the exact compiled variant (e.g. `py312h58c1407_0`).
- **Channel** — the package source (here always `conda-forge`).
- **Platform** — the target OS/arch (`linux-64`, `win-64`, `osx-arm64`).
- **conda-lock** — the tool that solves once and writes the lockfile.
- **mamba** — the fast solver conda-lock uses under the hood.
- **Intent vs. state** — loosely-pinned `.yml` (what you want) vs. frozen lock (what you got).
