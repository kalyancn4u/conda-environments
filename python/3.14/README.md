## ⚠️ Python 3.14 readiness

Python 3.14 (released Oct 2025) is **new**. This tree is at **structural parity with
[`python/3.12`](../3.12/)** (copy + version-pin bump to `python=3.14.*`, `py314-*`), and
**9 of the 14 environments/templates are solved and locked for `linux-64`** — generated by
the [`update-lockfiles`](../../.github/workflows/update-lockfiles.yml) workflow against
conda-forge and committed under [`lockfiles/linux-64/`](lockfiles/linux-64/). A successful
`conda-lock` solve *is* validation that those stacks resolve on 3.14. The rest wait on
upstream conda-forge builds — expected for such a new Python.

> **✅ Solved & locked (linux-64):** `01-core`, `02-ml`, `03-deep-learning` (PyTorch),
> `04-web`, `05-tools`, `07-geospatial`, and templates `minimal`, `data-science`, `mlops`
> (65–480 packages each).
>
> **⚠️ Not yet solvable on 3.14** (upstream conda-forge gaps, **not** repo bugs):
> | Target | Blocked on |
> | :--- | :--- |
> | [`06-tensorflow`](environments/06-tensorflow.yml) · [`all-in-one-tflow`](templates/all-in-one-tflow.yml) | **TensorFlow** has no conda-forge 3.14 build |
> | [`08-timeseries`](environments/08-timeseries.yml) | the forecasting stack (`prophet` / `cmdstanpy` / `sktime` / `statsforecast`) |
> | [`llm`](templates/llm.yml) | its retrieval/HF extras (e.g. `faiss`, `sentence-transformers`) beyond the PyTorch base |
> | [`all-in-one-pytorch`](templates/all-in-one-pytorch.yml) | unions the `08-timeseries` gap above |
>
> Use [`python/3.12`](../3.12/) (or [`3.13`](../3.13/)) for these workloads until the builds
> land, then re-run the workflow for the missing targets:
> ```bash
> gh workflow run update-lockfiles.yml -f version=3.14 -f platforms="linux-64"
> ```

**uv `requirements/*.txt` are committed for 12 of 14 targets** (PyPI wheels, `linux`,
Python 3.14) under [`lockfiles/requirements/`](lockfiles/requirements/) — the production/CI
path, and it fills several conda-forge gaps: `08-timeseries`, `llm`, and `all-in-one-pytorch`
resolve fine from **PyPI** even though they don't yet solve on conda-forge. The only two
without a uv lock are `06-tensorflow` and `all-in-one-tflow` — **TensorFlow has no PyPI wheel
for 3.14** either. Only the `win-64`/`osx-arm64` **conda** locks remain on demand.

## Common commands

The helper scripts live in the shared [`scripts/`](../../scripts/) folder at the
repository root — run these **from the repo root** and pass **`-p 3.14`** to target this
tree.

```bash
# Create (Linux/macOS)
./scripts/create-env.sh -p 3.14 01-core

# Create (Windows PowerShell)
.\scripts\create-env.ps1 -p 3.14 01-core

# Update to match the YAML (prunes removed packages)
./scripts/update-env.sh -p 3.14 01-core

# Verify the key packages import
python scripts/verify-env.py -p 3.14 --env core

# Compare two environments / list upgradable packages
./scripts/compare-envs.sh py314-core py314-ds
./scripts/compare-envs.sh --outdated py314-core

# Reproduce CI locally: build + verify an env in the Miniforge container (needs Docker)
./scripts/test-env.sh -p 3.14 01-core        # one env      (Windows: .\scripts\test-env.ps1 -p 3.14 01-core)
./scripts/test-env.sh -p 3.14 --all          # every env
```

Wider workflows — the venv/uv, micromamba, security, and Jupyter helpers:

```bash
./scripts/doctor.sh -p 3.14                   # what's installed & configured? (read-only preflight)
./scripts/setup-venv.sh -p 3.14 04-web        # venv + pinned requirements (PyPI/production)
./scripts/micromamba-env.sh -p 3.14 01-core   # zero-install create + verify
./scripts/audit-env.sh -p 3.14 --name py314-web   # security: CVE scan + conda/pip clash check
./scripts/register-kernel.sh py314-ml     # expose an env as a Jupyter kernel
```

## Before you start

Set conda-forge as the default channel with strict priority (once per machine):

```bash
conda config --add channels conda-forge
conda config --set channel_priority strict
```

Platform caveats (full matrix in [docs/compatibility.md](../../docs/compatibility.md)):

- **TensorFlow** has no conda-forge **win-64** build — install via pip on Windows.
- **gunicorn** (in `04-web`) is POSIX-only — use `uvicorn`/`waitress` on Windows.
- All environments are **CPU-only**; see the CUDA section for GPU.
