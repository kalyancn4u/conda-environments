# Contributing

Thanks for helping keep these environments lean and reproducible. This project is
opinionated on purpose — the guidelines below are what keep it maintainable.

## Guiding principles

1. **Modularity over monoliths.** A new concern usually means a new small
   environment, not more packages bolted onto an existing one.
2. **conda-forge first.** Every dependency should resolve from `conda-forge`. If a
   package only exists on PyPI, add it under a `pip:` block and justify it in the PR.
3. **Minimal pinning.** Pin only when technically justified (a known-bad version, an
   ABI constraint, a reproducibility anchor). Document *why* in a comment.
4. **CPU by default.** Do not add CUDA/GPU packages to the YAMLs. GPU guidance lives
   in [docs/compatibility.md](docs/compatibility.md).
5. **Explain non-obvious choices.** A one-line comment above a package is cheap and
   saves the next maintainer an hour.

## Making a change

1. Edit the relevant `*.yml` under `python/<version>/environments/` (or a template).
2. Keep dependency lists **alphabetically sorted within their comment group**.
3. Validate locally:
   ```bash
   # YAML well-formedness + naming conventions
   python -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" python/3.12/environments/01-core.yml

   # Full solve (dry run) — proves the environment is still solvable
   conda env create --dry-run -f python/3.12/environments/01-core.yml
   ```
4. If you changed dependencies, note it in [CHANGELOG.md](CHANGELOG.md) under
   `[Unreleased]`.
5. Open a PR. CI (`validate` + `test-environments`) must pass.

## Adding a new Python version

Copy `python/3.12/` to `python/3.13/`, bump `python=3.13.*`, and re-solve. No other
directory needs to change — see [docs/architecture.md](docs/architecture.md).

## Lockfiles

Do **not** hand-edit files under `lockfiles/`. They are regenerated by the
`update-lockfiles` workflow (or `conda-lock` locally). Commit lockfile changes in a
dedicated PR so environment-intent changes stay reviewable.

## Commit style

Conventional-commit prefixes are appreciated (`feat:`, `fix:`, `docs:`, `chore:`),
but clear English wins over ceremony.
